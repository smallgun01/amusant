# Amusant Fast Voice contract (P2)

## Baseline and audio envelope

Gemini Live is the first real provider targeted. The app will select a provider explicitly; P2 is focused on one Gemini adapter, not a multi-provider UI or automatic fallback. Current code is a dependency-injected scaffold. Offline fake-session tests pass. A bounded Live text-to-speech smoke passed once: output transcript `Ready.`, non-cancelled turn_complete, and 48,000 bytes of 24 kHz PCM16LE (~1 second). The SDK marked the transcript event non-final; text matched at turn completion. Real microphone/PTT audio input remains untested.

For the initial Kai-compatible client boundary, internal audio is mono PCM16 little-endian with an explicit sample rate: 16 kHz input and 24 kHz output. The Gemini scaffold accepts 16 kHz input and requires output explicitly tagged as 24 kHz PCM; it rejects unknown/different output rates rather than silently mislabel audio. Resampling is not implemented yet; future adapters must normalize to this boundary. This matches pinned Kai v0.12.0's relay protocol and its `audio/pcm;rate=16000` Gemini input path; this is source-level evidence, not a new Amusant runtime test. See [Kai session.py at the pinned baseline](https://github.com/zbruceli/kai/blob/1681fb3c11acd28525d8987bba4b9bf4bc2a288f/relay/kai_relay/session.py).

## Contract semantics

- `start_turn`/`end_turn` represent PTT activity start/release. Kai v0.12.0 starts Gemini activity on PTT and its source comments that the activity start interrupts current speech. The adapter reports provider-reported interruption separately from turn completion.
- Output callbacks are dispatched serially in provider receive order; async callbacks are awaited. Transcripts label input/output and partial/final state.
- Tool calls carry provider call ID, name, and JSON arguments; results return against the same ID.
- `barge_in` and standalone `cancellation` are separate capabilities. Gemini's adapter marks barge-in supported but standalone cancellation unsupported; `cancel_response()` fails closed until a verified provider operation exists.
- `close` releases the live session and receive loop. Background receive failures surface as sanitized `ProviderError` events; no credentials/audio are included.
- Provider selection is exact and fail-closed: absent/unknown choice is an error, never implicit Gemini or alternate-provider fallback.

## Runtime configuration and current verification boundary

`build_live_provider(environ)` is the fail-closed startup wiring. It requires `AMUSANT_LIVE_PROVIDER=gemini` and a runtime-injected `GEMINI_API_KEY`; it accepts an optional `AMUSANT_GEMINI_MODEL`. The default model is copied from Kai v0.12.0's `.env.example` (`gemini-3.8-live`) and is listed by the user's API project. A bounded text-to-speech smoke produced a transcript and about one second of PCM. Real Kai-sim PTT-to-Live runtime acceptance passed once with cap128, including a complete audible speaker response; an earlier cap64 turn was truncated, and the cap correlation does not yet prove a single root cause. See STATUS.md for runtime evidence. In AWS, map the JSON property `Amusant_Google_API` from Secrets Manager to the container environment variable `GEMINI_API_KEY`; do not put the value in task definition text, image, repository, or logs. For local tests, inject the variable only in the process environment.

The `GeminiLiveProvider` maps the SDK surface (`connect`, `send_realtime_input`, `receive`, `send_tool_response`) through client/type objects. `google-genai>=2.0` is declared and locked to 2.29.0, installed only in repo `.venv`. Twenty-five root `uv run` tests pass, including fake-session tests, offline config construction with actual SDK types, output token limit validation, and fake-provider PTT bridge integration. The isolated P1 relay suite has 4 tests. Offline tests validate startup config/type construction and fake-provider PTT bridge behavior. Real Live text-to-speech smoke passed. A real Kai-sim PTT Live turn returned a model text response and completed; the cap-128 turn logged 152,576 input bytes, turn_complete, and 92,642 output bytes (~1.93 s PCM), and the user confirmed full speech playback. This passes the current P2 runtime voice-loop gate once.
