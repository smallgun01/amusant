# Grok Routine webhook compromise: security boundary and response

Status: **Draft for Owner review**, 2026-10-29. Scope: [#146](https://github.com/smallgun01/amusant/issues/146), [#134 F1](https://github.com/smallgun01/amusant/issues/134), [#127](https://github.com/smallgun01/amusant/issues/127). Source baseline: `main@e178725fa17f4ea011baa7f6bc81b8fa0a55cc4d`. Cursor documentation checked 2026-10-29. Product documentation is evidence of advertised capability, not evidence of this Owner's settings or of a live security test.

## Decision and priority

**P0 — unresolved exfiltration boundary.** A stolen Routine bearer can submit instructions to a Bot which acts with the member's accessible data and tools. If it can read private content and send to an attacker-controlled destination, neither a fixed callback in a prompt nor Relay's proxy stops exfiltration from Cursor's hosted computer. A stolen key alone does not grant arbitrary GitHub access directly; the Bot's actual grants and channels determine impact. **NOT VERIFIED:** the Owner's plan, app permissions, routing, approval rules, and the effect of any network policy. Until Owner establishes an enforceable boundary or explicitly accepts residual exposure, do not authorize sensitive private data and unrestricted outbound channels together.

**P0 — result capability exposure.** The per-task result bearer is in the webhook payload and can be visible in provider execution/model context. A holder can race to submit a schema-valid result for that task while valid. Hashing at rest, TLS and header placement on callback do not hide it from that context. Exact-token echo rejection does not prevent transformations, fragmentation, or disclosure through other tools, logs or artifacts.

**P1 — drift, replay and operational recovery.** Repeated webhook calls can start multiple runs; no provider-side nonce or signature replay protection was established. Routine drift or stale credentials can produce missing callbacks or route data incorrectly. Rate limits are not authorization or replay protection. Rotation, in-flight revocation and audit completeness are **NOT VERIFIED**.

## Current source boundary

- [Executor](../../relay/grok_callback_executor.py) validates a server-configured HTTPS callback URL with fixed path; inserts it into an instruction alongside the task text, and sends a generated task token in the JSON payload. It does not perform a deterministic comparison against a separately configured Grok Routine destination. The task text is untrusted once the key is compromised. The model can ignore or reinterpret the instruction. One POST, no redirect and no automatic retry; HTTP 200 means acceptance, not completion; other outcomes remain conservatively unknown.
- [Receiver](../../relay/grok_callback.py) accepts only the callback path, exact configured Host and bearer header, bounded JSON and schema, rejects duplicate JSON keys and exact capability appearing in the body. [Listener](../../relay/callback_listener.py) checks private bind and canonical host mapping; TLS termination is an external gate. Host checking authenticates neither the sender nor outbound destination.
- [TaskStore](../../relay/task_store.py) hashes the token, checks Owner/task, expiry and revocation, and commits receipt/results/Inbox atomically. A same-digest replay returns the original receipt and a different digest conflicts only after the Owner/task capability passes token, revocation and expiry checks. After Owner abandon, a late report is retained as metadata without reopening or speaking only while that capability remains unrevoked and unexpired; otherwise it is rejected. This is callback idempotency, not protection against a stolen webhook key initiating new runs. A bearer is not proof that the intended Bot authored the result.
- [Compose](../../deploy/oci-a1/compose.grok.yaml) supplies a secret file for the Routine token, private networks, restricted Relay and egress proxy. Those are Relay-side controls, **not Grok hosted-computer network controls**. Source config does not prove deployment or edge TLS/logging. [Callback tests](../../relay/tests/test_grok_callback.py), [listener tests](../../relay/tests/test_callback_listener.py), and [runtime tests](../../deploy/oci-a1/tests/test_grok_runtime.py) cover offline contracts including token/owner/expiry, replay and deployment configuration; they cannot prove native Grok permissions or egress policy. No tests were run or real secrets read for this documentation review.

## Fixed destination: recommended fail-closed contract

Today the Routine's callback destination is instruction/configuration text, not a proven provider-enforced outbound destination. Relay cannot enforce destinations of separate requests from Cursor's hosted computer. No deterministic Grok-side pre-egress validation hook has been identified. As a future contract, Owner would maintain one trusted HTTPS callback destination in Routine configuration and Relay configuration. A payload candidate, if one exists, is **only** an equality assertion. Compare against the Owner-controlled value in a deterministic component outside model judgment before any outbound request; reject a missing required candidate, malformed URL, duplicate/conflicting value, or mismatch, and report a sanitized configuration error without sending to either candidate or alternate host. Define canonical comparison once (scheme, host, port, exact path; reject userinfo, query and fragment) and test edge cases. If no trusted deterministic Grok-side enforcement exists, mark this as a **proposed follow-up**, not a present protection. Do not add an arbitrary callback proxy or second agent framework. Enforced network rules still must cover other tools and channels.

## Owner minimum configuration checklist

1. **Before sensitive work:** establish the data classification and approved repositories/files. Prefer a dedicated Cursor member with no unrelated logins or workspace contents; restrict GitHub installation and account privileges at GitHub, remove unused apps, revoke source-service authorizations and browser sessions. Confirm all Bots sharing the member computer. Record only nonsecret scope evidence.
2. In desktop Bot details → Routine, check instruction, trigger, fixed callback, and paused/active state against an Owner-controlled baseline. Restrict who can modify the member, app grants and routine; verify practical scope in App. Ask for approval before sending, publishing, external communication, writes and changes to routines. Treat instruction text as guidance, not a firewall.
3. If Enterprise is available, configure **Team Allowlist Only** with only necessary destinations, enable **Apply to MCP servers**, review group overrides and lock where appropriate, disable unnecessary local egress routing and local execution, and restrict connector marketplace access. Confirm real enforcement and essential destinations through separately authorized safe tests. A fixed callback host is not sufficient if other allowed services can receive attacker-controlled data; GitHub write-capable repositories, issues, comments, gists or other allowed write surfaces can carry data even on an allowlisted domain. Restrict grants to read-only wherever possible.
4. Require narrowly scoped Ask first rules and Enterprise enforcement where available; review targets and input before approving, avoid broad auto-allow. Confirm the unattended callback workflow separately. A callback waiting for approval may cause timeout; do not invent a native approval state.
5. Protect Routine key and result tokens in secret storage; no values or private URLs in issues, screenshots, logs or chat. Check log redaction and access control. Keep callback TTL short enough for intended work and monitor unexpected runs/usage. Configure available audit/recording and retention only with Owner approval.
6. **Go/no-go:** Owner verifies plan, effective policy, connected grants and approval behavior, then approves the remaining risk. If network restrictions cannot be enforced, remove sensitive access or pause the Routine; a prompt-only setup does not close P0. Live verification requires separate exact-case authorization.

## Suspected compromise runbook

1. **Contain:** Owner pauses the affected Routine in App immediately; stop new local admissions by the approved operational procedure. Do not assume pausing cancels running jobs or that local abandon stops the remote Bot. Preserve timestamps and nonsecret identifiers.
2. **Limit access:** Owner reviews and removes unnecessary connected apps, revokes grants at source services, signs out browser sessions and removes exposed files as appropriate. Investigate other Bots sharing the member's computer. Restrict network and approvals if entitled and authorized. Do not silently change production or infrastructure.
3. **Revoke and rotate:** Treat the old key as compromised. Owner checks App/support for actual regeneration, revocation propagation, URL change and in-flight behavior; if unavailable, keep the old routine paused and consult Cursor about deletion/replacement and invalidation. Do not assert that deleting/recreating automatically rotates or revokes. Update sender secret via approved secret-management deployment only after a verified replacement; never publish values. Preserve relevant evidence before reconciliation. For an eligible Grok task, the existing audited `operator_reconcile_uncertain(..., terminal_state='abandoned', revoke_callback_token=True)` revokes the per-task callback capability and releases only the local single-flight slot; it does not stop Grok remotely. Eligibility requires a running/uncertain Grok callback task, dispatch started, an eligible claimed/sent/uncertain outbox, no receipt and the required operator/evidence inputs. Revoked late callbacks fail authentication rather than being retained as metadata. Other states do not have this revocation path; assess them separately. Rotate other exposed credentials separately.
4. **Investigate:** preserve access-controlled run history, audit/action records if available, GitHub/source-service events and safe metadata. Correlate times and task IDs without raw payloads, bearer headers, private content or URLs in public records. Determine accessible data and possible destinations; absence of logs is not proof of no exfiltration.
5. **Recover:** Owner confirms old trigger invalidation, trusted destination, minimal grants, effective network/MCP and approval rules, token lifecycle and monitoring; conduct only separately authorized synthetic verification. Reconcile uncertain tasks without replay or assuming remote stop. Resume only after explicit risk acceptance and record unresolved **NOT VERIFIED** items. Escalate to Cursor support and appropriate incident owners when required.

This research adds no new runtime component, makes no provider calls, and does not establish deployed or device end-to-end PASS.
